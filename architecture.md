# AI-рекрутер MOVmedia — архитектура

## 1. Принцип работы

Диалог ведётся через Gemini API поверх системного промпта, в который на каждый ход подставляется вся база знаний (компания, вакансии, тестовые задания, ссылки, FAQ) и известный на данный момент профиль кандидата. Жёсткого дерева сценариев нет — модель сама решает, как вести разговор, опираясь на правила и данные в промпте. Технические события (передача кандидата рекрутеру, обновление стадии, сохранение данных кандидата) модель инициирует с помощью вызовов инструментов, которые код-обвязка выполняет напрямую в Telegram и в SQLite.

Это соответствует требованиям технического задания: не сценарный бот с фиксированными ответами, а интеллектуальный ассистент, ведущий естественный диалог, который никогда не оставляет кандидата без ответа.

## 2. Пользовательский поток

```
/начало
  │
  ▼
Приветствие + краткое описание компании + ссылка на сайт
  │
  ▼
"На какую вакансию откликаетесь?" ←──────────────┐
  │                                                │
  ├─ кандидат сразу называет вакансию              │
  ├─ кандидат сначала спрашивает о компании ───────┘ (отвечает, потом
  │                                                    возвращается к вопросу)
  ├─ кандидат сразу просит тестовое → уточняет вакансию, если не указана,
  │  и выдаёт тестовое сразу, без лишних вопросов
  │
  ▼
Краткая карточка вакансии (обязанности/требования/условия)
  │
  ▼
Сбор анкеты: имя, резюме (файл/ссылка) — как только что-то стало известно,
сразу вызывается update_candidate_profile
  │
  ├─ вакансия БЕЗ тестового (Project-менеджер) ──────┐
  │                                                    │
  ▼ вакансия С тестовым (PR-менеджер)                 │
Выдача тестового (ссылка + объяснение критериев        │
и политики сроков), ссылка фиксируется в sent_links    │
  │                                                    │
  ▼                                                    │
Приём выполненного тестового                           │
  │                                                    │
  └────────────────────────────────────────────────────┘
  │
  ▼
Финальная сводка → notify_recruiter(candidate_summary) → Алине
  │
  ▼
Прощание, следующие шаги, "будем рады работать вместе"
```

Параллельно в любой момент диалога кандидат может: задавать вопросы о компании/вакансии/процессе (детекция → поиск в базе знаний → ответ или честная эскалация); просить прямой контакт с рекрутером (после 2-го запроса эскалирует и сообщает срок ответа); сообщить, что передумал (вежливое завершение + уведомление рекрутеру); выражать тревогу или раздражение (бот отвечает эмпатично, поддерживает или извиняется и предлагает решение); пропасть на несколько дней после получения тестового (отслеживается фоновым процессом, не самим диалогом).

Отдельно, вне этого диалога, рекрутер может в любой момент командой `/status <chat_id> <stage> [комментарий]` перевести кандидата на стадию, которая решается не ботом, а человеком (screening, интервью, review, offer, rejected) — кандидат при этом сразу получает шаблонное уведомление.

## 3. Обработка вопросов кандидата

Любой вопрос (в том числе без "?", например "когда интервью", "не открывается ссылка", "можно перенести встречу", "где тестовое") обрабатывается по цепочке: 1) определить, о чём вопрос; 2) проверить базу знаний (company/vacancies/test_assignments/links/FAQ); 3) если есть точный ответ — ответить из базы; 4) если ответа нет — никогда не придумывать, честно сообщить кандидату и вызвать `notify_recruiter(reason="unknown_question")` с вопросом дословно.

## 4. Состояния и память кандидата

Хранятся в SQLite (`storage.py`), одна запись на chat_id Telegram:

- `history` — полная история сообщений для контекста Gemini (включая tool-calls и их результаты);
- `stage` — техническая стадия из полного словаря: `applied`, `screening`, `test_sent`, `test_received`, `interview_scheduled`, `interview_completed`, `review`, `offer`, `rejected`, `withdrawn`. Стадии `test_sent`, `test_received`, `withdrawn` модель выставляет сама по ходу диалога через `update_candidate_stage`; остальные выставляет рекрутер вручную командой `/status`;
- `stage_updated_at` — время последнего изменения стадии, используется для обнаружения "пропавших" кандидатов;
- `flagged_silent` — чтобы не уведомлять рекрутера об одном и том же молчащем кандидате повторно;
- `name`, `vacancy`, `interview_date`, `salary_expectations` — структурированная память о кандидате, обновляется моделью через `update_candidate_profile`, чтобы бот никогда не переспрашивал уже известное;
- `sent_links`, `uploaded_files`, `previous_questions` — списки отправленных кандидату ссылок, полученных от него файлов и заданных ранее вопросов, для полноты памяти о диалоге.

Известный профиль кандидата на каждый ход подставляется в системный промпт отдельным блоком "Известно о кандидате", чтобы модель явно видела, что уже знает, и не задавала повторных вопросов.

## 5. Надёжность обращения к AI (никогда не оставлять кандидата без ответа)

`gemini_client.py` оборачивает каждый HTTP-запрос к Gemini (generateContent) в повторные попытки с экспоненциальной паузой (`_request_with_retry`, по умолчанию 3 попытки). Если все попытки исчерпаны, поднимается `GeminiError`.

`bot.py` (функция `run_and_reply`) обязательно ловит это исключение: кандидату отправляется вежливое fallback-сообщение о технических сложностях вместо тишины, входящее сообщение сохраняется в историю для последующего анализа, а рекрутеру автоматически уходит уведомление о сбое, чтобы он мог подключиться вручную. Все ключевые события (входящее сообщение, обращение к Gemini, использование fallback, смена стадии, ошибки) пишутся в структурированный лог через `logging`.

## 6. Структура базы знаний

Шесть markdown-файлов в папке `knowledge/`, полностью независимые от кода и удобные для правки нетехническим человеком:

- `knowledge/company.md` — сайт, позиционирование, клиенты, политика зарплат, рекрутер;
- `knowledge/hiring_process.md` — этапы отбора после чата с ботом;
- `knowledge/vacancies.md` — по разделу на вакансию: описание, обязанности, требования, условия, отметка о наличии тестового задания;
- `knowledge/test_assignments.md` — детали тестовых заданий (ссылка, формат сдачи, критерии оценки, политика сроков) для вакансий, где они предусмотрены;
- `knowledge/links.md` — прочие проверенные ссылки (сайт, контакты рекрутера);
- `knowledge/faq.md` — вопрос/ответ.

`system_prompt.py` на каждый вызов подставляет текст всех этих файлов целиком в системный промпт (без промежуточного JSON) и собирает единый системный промпт вместе с профилем кандидата. Функция `known_test_task_links()` регулярным выражением вытаскивает все ссылки из `test_assignments.md` — по ним `bot.py` определяет, что кандидату была отправлена ссылка на тестовое, и сохраняет её в `sent_links`. Чтобы добавить вакансию, изменить FAQ или обновить тестовое задание — достаточно отредактировать соответствующий `.md`-файл в `knowledge/`, без изменения кода бота.

## 7. Логика передачи кандидата HR

Модель никогда не отправляет сообщения Алине напрямую — она только формулирует текст и вызывает инструмент `notify_recruiter(reason, message)`. Код-обвязка (`bot.py`) получает этот вызов и реально отправляет сообщение в `RECRUITER_CHAT_ID` через Telegram Bot API. Так исключается риск, что модель "придумает" отправку, которой не было.

Файлы (резюме, выполненное тестовое) обрабатываются отдельно от модели: как только Telegram-сообщение содержит `document` или `photo`, `bot.py` немедленно и напрямую пересылает его в `RECRUITER_CHAT_ID` и сохраняет `file_id` в память кандидата (`uploaded_files`), независимо от того, что в этот момент "думает" модель.

Стадии, требующие решения человека (screening, интервью, review, offer, rejected), рекрутер выставляет командой `/status` — кандидат получает автоматическое шаблонное уведомление с подтверждением, следующим шагом и приглашением задать вопросы.

## 8. Рекомендации по масштабированию

Новые вакансии — добавить раздел в `knowledge/vacancies.md` и, если нужно, в `knowledge/test_assignments.md`. Новые тестовые задания — сейчас формат текстовый (ссылка + описание в markdown); для файловых тестовых можно расширить раздел и логику в `system_prompt.py`. Расширение FAQ — просто дописывать пары вопрос/ответ в `knowledge/faq.md`. Более сложная эскалация (например, разным рекрутерам под разные вакансии) — потребует доработки кода (например, отдельного поля с chat_id рекрутера под конкретную вакансию). Рост нагрузки — вынести `check_silent_candidates` в отдельный процесс/воркер, а SQLite заменить на Postgres.

## 9. Ограничения текущей версии

Не отслеживается автоматически, сколько раз кандидат просил рекрутера — модель определяет это из полной истории диалога; при очень длинных диалогах имеет смысл периодически суммаризировать историю. Один Telegram-бот = один процесс с polling — для нескольких вакансий с разными рекрутерами или высокой нагрузкой лучше перейти на webhook-режим. Стадии, которые решает человек (screening, интервью, review, offer, rejected), переводятся вручную командой `/status` в чате рекрутера — полноценной админ-панели пока нет.
